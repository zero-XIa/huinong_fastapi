### 问诊模块关键差异详解

#### session\_id 上下文机制的核心偏差

论文第 58 行描述了一个**后端主动检索+注入上下文**的机制：

> 「后端根据 session\_id 从 tb\_message 表中检索最近三轮对话记录，发现上文语境后将历史对话与当前追问一同发送至 Dify」

但实际实现（[chat.py:L46-L47](file:///d:/Code/Python/HuiNong/app/api/endpoints/chat.py#L46-L47)）是：

```python
dify_conversation_id = session.dify_conversation_id
# 然后将此 conversation_id 传给 Dify 的 /chat-messages API
```

这是**依赖 Dify 平台的 conversation\_id 原生机制**来维护上下文，而非后端检索历史消息。

**两者区别：**

- **论文描述**：后端从 MySQL 查消息 → 拼接到请求 → 发给 Dify（无状态方式）
- **实际实现**：保存 Dify 返回的 conversation\_id → 后续请求原样带回 → Dify 内置上下文管理（有状态，依赖 Dify）
